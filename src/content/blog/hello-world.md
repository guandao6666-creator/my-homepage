这个博客被我从零开始重写了三次。

第一次是为了"有一个自己的网址"，第二次是为了"用上更新的框架"，第三次——也就是现在这版——我才第一次在动手之前问了自己一个问题：

**它到底是给谁看的？**

## 前两次错在哪

第一次搭建时，我花了三个晚上挑主题、调字体、改配色。文章只有两篇，其中一篇还是"Hello World"。

第二次稍微好一点，我加了暗色模式、阅读进度条、代码高亮——所有博客都有的东西我都有了。然后我停了半年没更新。

问题不在技术。问题在于，我把它当成了一个**作品**，而不是一个**工具**。

作品需要观众，没有掌声就会停。工具只需要使用者——也就是三年后的我自己。

## 现在这套逻辑

想清楚这一点之后，很多决定突然变得简单：

- **不追更新频率**。写不出来就不写，硬凑的东西我自己都不会回看。
- **先保证可检索**。所以标签、搜索、归档比动效重要。
- **内容与表现分离**。文章是数据，页面是视图，改版不应该动到内容。
- **能一个人维护**。不引入我半年后会忘记怎么部署的服务。

最后一条尤其关键。我见过太多个人项目死于"配置太复杂，下次想改的时候已经忘了从哪开始"。

## 技术上的取舍

这一版用 Astro。选它的理由很朴素：

```bash
# 构建时把 Markdown 变成纯静态 HTML
npm run build   # → dist/ 里全是 HTML，没有任何运行时 JS
```

页面在构建时生成，用户打开时只有一个 HTML 文件和一点点内联脚本。没有 hydration，没有首屏白屏，没有"框架加载失败"。

内容这一层，我拆成了两部分：

1. 文章正文最终以 Markdown 形式进入内容集合，构建期渲染；
2. 文章的**事实来源**放在云端数据库里，构建前同步下来。

这样写作可以在任何设备上进行，而线上永远是一份静态文件，快且稳。

> 好的架构不是让你能加更多东西，而是让你以后想改的时候，知道该改哪里。

## 一点自我提醒

我在草稿里给自己留了一句话，贴在编辑器顶上：

> 写不清楚，通常不是文笔问题，是还没想清楚。

所以这个博客真正的功能，可能不是"展示"，而是**逼我把模糊的想法推到能被别人读懂的程度**。

如果你也正在搭自己的站点，我的建议是：先写十篇，再考虑设计。
